# Integrity Verification

This document describes the cryptographic integrity verification processes used by Taurus-PROTECT SDKs. These verification flows ensure data authenticity and proper authorization.

## Overview

The SDKs implement cryptographic verification at multiple points to ensure:

- **Data Integrity** - Data hasn't been tampered with in transit or at rest
- **Authorization** - Actions were approved by the correct parties
- **Non-repudiation** - Approvers cannot deny having signed
- **Audit Trail** - All signatures are recorded for compliance

---

## What Gets Verified

| Entity | Verification | Flow |
|--------|--------------|------|
| **Governance Rules** | SuperAdmin signatures on the rules container, counted by DISTINCT key | [below](#governance-rules-verification) |
| **Whitelisted Address** | Metadata hash + SuperAdmin signatures + user signatures + parse from the verified payload | [6 steps](#whitelisted-address-verification) |
| **Whitelisted Asset** (= whitelisted contract) | The same chain, against `ContractAddressWhitelistingRules` | [5 steps + parse](#whitelisted-asset-verification) |
| **Request Metadata** | SHA-256 hash of the payload string, constant-time | [below](#request-metadata-verification) |
| **Address** | HSM-slot signature proves the address was generated by the HSM | [below](#address-verification) |
| **Price** | `PRICEUPDATER` signature over the canonical five-field projection | [below](#price-verification) |

Verification is **mandatory everywhere**. Every SDK refuses to construct a client without
SuperAdmin keys, and there is no read path on any of these entities that returns unverified
data. Where two services once read the same entity — the whitelisted asset — the unverified
one is gone rather than deprecated, because a bypass that still compiles is a bypass someone
will reach for.

## Governance Rules Verification

Governance rules define who can approve transactions and whitelist addresses. They are signed by SuperAdmins.

### Data Structure

```
GovernanceRuleset
├── rulesContainer     (Base64-encoded protobuf)
├── signatures[]       (SuperAdmin ECDSA signatures)
└── locked             (Whether rules can be modified)
```

### Verification Process

1. **Decode rules container** - Base64 decode to raw bytes
2. **Calculate hash** - SHA-256 of the raw bytes
3. **Identify the distinct signers** - For each signature:
   - Decode Base64 signature
   - Try verification against each configured SuperAdmin public key
   - On success, record the **signing key** (identified by a SHA-256 hash of its
     encoded public key), so the same key counts once however many entries it appears in
4. **Check threshold** - Ensure the number of **distinct signing keys** is at least
   `minValidSignatures`

> **`minValidSignatures` counts distinct signing keys, never signature entries.** ECDSA is
> randomized, so one key can produce unlimited valid signatures over the same container.
> Counting entries — or de-duplicating by the server-supplied `userId` — would let a single
> compromised SuperAdmin key satisfy any threshold, making 2-of-N no stronger than 1-of-N.
> A key configured twice counts once. This is enforced in each SDK's single
> `signature_verifier` helper, which also serves the whitelisted-address and
> whitelisted-asset paths.

### Which reads verify

**All of them, in all four SDKs.** This container carries the HSM public key that address
verification trusts, so an unverified one is the worst object the SDK can return.

| Read | Verifies | Note |
|---|---|---|
| `getRules` | yes | |
| `getRulesById` | yes | |
| `getRulesHistory` | yes, **leniently** | excludes + names unverifiable entries; see below |
| `getDecodedRulesContainer` | yes, unconditionally | no keys ⇒ error, never a silent skip |
| `getRulesProposal` | **no, by design** | a proposal legitimately carries 0..N signatures — signing IS the approval step, so a threshold is an enforcement-time invariant, not a precondition for reading one |

**History is lenient where the single-ruleset reads are strict.** A SuperAdmin key rotation
makes every pre-rotation ruleset unverifiable, so a strict page would deny access to the
whole audit trail from the rotation onwards. It therefore excludes and NAMES what it
dropped (`ExcludedUnverified` / `excluded_unverified` / `excludedUnverified`), reduces
`totalItems` accordingly, and does **not** error when nothing survives. A consumer that
receives that list must surface it: dropping it turns "some entries were withheld" into
"there are none".

**Verification is memoised, not repeated.** Keyed on
`sha256(containerBytes) || sha256(canonical signature list)` — successes only, so a failure
resurfaces its error on every call, and a re-signed container is a cache miss. This is what
makes per-entry history verification affordable: a page repeats the same container across
entries, so it costs one ECDSA pass per *distinct* container. It is deliberately **not** a
second container cache — `RulesContainerCache` already holds the decoded+verified container
for the address/asset/price paths.

### Failure Conditions

- Hash calculation fails
- Signature decode fails
- No signature matches any SuperAdmin key
- Fewer valid signatures than required threshold
- No SuperAdmin keys configured — the service cannot be constructed that way in any SDK

## Whitelisted Address Verification

Whitelisted addresses undergo comprehensive multi-step verification.

### Data Structure

```
WhitelistedAddress
├── metadata
│   ├── payloadAsString   (Raw JSON for hashing)
│   └── hash              (Expected SHA-256 hash)
├── rulesContainer        (Governance rules)
├── rulesSignatures       (SuperAdmin signatures)
└── signedAddress
    ├── payload           (Base64-encoded address data)
    └── signatures[]      (User approval signatures)
        ├── userSignature
        │   ├── userId
        │   └── signature
        └── hashes[]      (Hashes covered by this signature)
```

### 6-Step Verification Flow

```
┌─────────────────────────────────────────────────────────────────────┐
│              STEP 1: Verify Metadata Hash                           │
│  SHA-256(payloadAsString) == metadata.hash ?                        │
│  Uses constant-time comparison to prevent timing attacks            │
└─────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────┐
│         STEP 2: Verify Rules Container Signatures                   │
│  SuperAdmin signatures on rulesContainer >= minValidSignatures      │
│  Uses ECDSA P-256 signature verification                            │
└─────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────┐
│              STEP 3: Decode Rules Container                         │
│  Base64 -> Protobuf -> Decoded rules structure                      │
│  Contains groups, users, and approval thresholds                    │
└─────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────┐
│         STEP 4: Verify Hash Coverage                                │
│  metadata.hash must appear in at least one signature.hashes[]       │
│  Ensures the payload hash was actually signed                       │
└─────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────┐
│         STEP 5: Verify User Signatures                              │
│  User signatures meet governance threshold requirements             │
│  Parallel paths (OR) -> Sequential groups (AND) -> Min signatures   │
└─────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────┐
│    STEP 6: Parse WhitelistedAddress from Verified Payload           │
│  Parse the verified payloadAsString JSON into domain model          │
│  All fields come from the cryptographically verified source         │
└─────────────────────────────────────────────────────────────────────┘
```

### Step Details

#### Step 1: Metadata Hash Verification

**Purpose:** Ensure the payload data hasn't been tampered with.

**Process:**
1. Compute SHA-256 hash of `metadata.payloadAsString`
2. Compare with provided `metadata.hash`
3. Use constant-time comparison to prevent timing attacks

#### Step 2: Rules Container Signature Verification

**Purpose:** Verify that SuperAdmins approved the governance rules.

**Process:**
1. For each signature in `rulesSignatures`:
   - Verify against SuperAdmin public keys
   - On success, record the signing key's fingerprint
2. Ensure the number of **distinct signing keys** is at least `minValidSignatures`
   (see the note under "Governance Rules Verification" — entries are never counted)

#### Step 3: Decode Rules Container

**Purpose:** Extract governance structure for threshold verification.

**Contains:**
- User groups with member IDs
- Parallel threshold paths (OR logic)
- Sequential group thresholds (AND logic)
- User public keys for signature verification

#### Step 4: Hash Coverage Verification

**Purpose:** Confirm the metadata hash is covered by at least one signature.

**Why needed:** Signatures cover a list of hashes. This ensures the specific address hash was actually included in what was signed.

**Process:**
1. Get `metadata.hash`
2. Check each `signature.hashes[]` list
3. At least one signature must include this hash

#### Step 5: User Signature Verification

**Purpose:** Verify user approvals meet governance threshold requirements.

**Governance Structure:**
```
ParallelThresholds (OR paths)
  └── SequentialThresholds (AND groups within a path)
        └── GroupThreshold
              ├── groupId
              └── minimumSignatures
```

**Algorithm:**
1. Find applicable rules based on blockchain/network
2. Determine thresholds based on linked wallets/addresses
3. Try each parallel path (OR logic - only one needs to succeed):
   - For each sequential group in the path (AND logic):
     - Verify group threshold is met
   - If all groups pass: verification succeeds
4. Group threshold verification:
   - Find group by ID in rules container
   - For each signature from a user in this group:
     - Verify signature covers metadata hash (constant-time)
     - Verify signature using the user's public key **from the container**
     - Add that key's fingerprint to a set of signers
   - Require `|signers| >= minimumSignatures`

```
  entry ─▶ in this group? ──no──▶ skip (not an error)
              │yes
              ▼
           covers the metadata hash? ──no──▶ skip, reason recorded
              │yes
              ▼
           user + key in the container? ──no──▶ skip, reason recorded
              │yes
              ▼
           signature over hashes-JSON valid? ──no──▶ skip, reason recorded
              │yes
              ▼
           signers[fingerprint(key)] ──▶ |signers| >= minimumSignatures? ──yes──▶ PASS
                                              │no
                                              ▼
                                       next entry; exhausted ─▶ IntegrityError
```

> **The unit is a SIGNER, not a signature entry.** The entries are decoded from the
> server-supplied `userSignatures` blob, so counting them let a *duplicated* entry from one
> group member satisfy an N-of-M group — copy the entry a single member really signed and an
> under-approved whitelist entry reads as approved. ECDSA is randomised, so re-signing works
> the same way. The signer is identified by a hash of the public key **the verified container
> holds for that user**, never by the entry's `userId`: two user IDs sharing one key are one
> compromised secret and count once.

> **A populated group with `minimumSignatures = 0` is rejected as malformed.** There is no
> post-loop threshold check — the only success exit is inside the loop once the signer set
> reaches the threshold — so a zero would silently mean "one signature suffices", turning a
> 2-of-N group into 1-of-N. An *empty* group with a zero threshold is fine: there is nobody
> to sign.

> `minimumSignatures` (per-group) and `minValidSignatures` (SuperAdmin, tenant-wide) are
> different thresholds and must not be unified. What differs is **scope**, not the counting
> rule — both count distinct signing keys. Both are gated cross-SDK by
> `scripts/resources/verification-signed-fixtures.json`, which carries a `superadmin_threshold`
> and a `group_threshold` section of real signatures; each section includes a vector where the
> entry count meets the threshold but the distinct-signer count does not, so an implementation
> that counts entries cannot pass the file.

#### Step 6: Parse the Whitelisted Address from the Verified Payload

**Purpose:** Make sure the returned object carries only values that were actually signed.

Steps 1-5 prove the envelope is authentic; step 6 is what stops an unsigned value reaching
the caller. The security-critical fields (`address`, `label`, `memo`, `customerId`,
`addressType`, and for assets `name`, `symbol`, `contractAddress`, `blockchain`, `network`)
are read **only** from the verified payload. If the payload omits a field, the result is
empty for that field — the value is never back-filled from the unverified DTO. Non-security
fields (`status`, `action`, `rule`, `createdAt`) may come from the DTO.

This step is why the flow is described as six steps rather than five: without it a caller
could verify every signature and still read an attacker-supplied label.

## Whitelisted Asset Verification

Whitelisted assets (contract addresses) run the same chain as addresses, against
`ContractAddressWhitelistingRules` instead of `AddressWhitelistingRules`.

```
  STEP 1  SHA-256(payloadAsString) == metadata.hash          (constant-time)
  STEP 2  SuperAdmin signatures on rulesContainer >= minValidSignatures
  STEP 3  Decode the rules container
  STEP 4  metadata.hash — or a LEGACY hash — covered by a signature
  STEP 5  User signatures meet the governance thresholds
  ──────  the hash step 4 matched is what step 5 checks, not metadata.hash
  STEP 6  Parse the WhitelistedAsset from the VERIFIED payload
```

### Differences from the address flow

| | Address | Asset |
|---|---|---|
| Rules type | `AddressWhitelistingRules` | `ContractAddressWhitelistingRules` |
| Thresholds | may be narrowed by matching rule *lines* | `parallelThresholds` directly, no lines |
| Legacy hashes | drop `contractType`, drop `label` inside `linkedInternalAddresses`, drop both | drop `isNFT`, drop `kindType`, drop both |

**The two legacy-hash functions are different and must stay different**
(`ComputeLegacyHashes` vs `ComputeAssetLegacyHashes`). Each has exactly three strategies,
applied in that order, de-duplicated.

### Step 4 returns the hash it matched

An asset signed before `isNFT` entered the schema is covered by the LEGACY hash, not by
SHA-256 of today's payload. Step 4 therefore returns the hash that was actually covered, and
step 5 checks signatures against *that* hash. A step 4 that returns nothing and lets step 5
re-read `metadata.hash` makes such an asset pass step 4 and then fail step 5.

### Fields

`name`, `symbol`, `contractAddress`, `blockchain`, `network` and `decimals` come **only** from
the verified payload. If the payload omits one, the result is empty for that field — never
back-filled from the DTO.

### A whitelisted asset and a whitelisted contract are ONE entity — with ONE reader

`/api/rest/v1/whitelists/contracts` is the only endpoint here. The SDKs used to expose it
twice: through the verified asset service, and again through the contract-whitelisting
service, which returned the envelope with no verification of any kind. TypeScript's copy was
worse — it parsed the signed payload and returned its contents as fact. Same endpoint, same
DTO, same eight fields that `createWhitelistedContract` writes: a caller who wanted to know
"is this contract whitelisted, and at what address?" had a verified answer and an unverified
one, and nothing pushed them toward the first.

The contract service is now **write-only** — create, approve, reject, update, delete,
attributes. Every read goes through the asset service:

```
  writes                             reads
  ──────                             ─────
  ContractWhitelisting               WhitelistedAsset
    createWhitelistedContract          get / getEnvelope
    approve* / reject*                 list                 ──▶ six-step chain
    update / delete                    listForApproval
    *Attribute                         approve (verified)
```

`listForApproval` exists on the verified reader for the same reason: the for-approval read
used to live *only* on the unverified service, so the rows a human inspects before approving
a contract address were the ones nothing had checked.

**Do not re-add a read to the contract service, or a mapper that takes a bare contract
envelope.** That is the shape of the bypass.

### Approving a whitelisted asset

The API takes **one** signature covering a JSON array of every metadata hash in the batch,
so there is no such thing as a partial approval. The verified path re-reads the batch, signs
the hashes *those* rows carry, and aborts the whole call if any row is missing or fails
verification:

```
  ids ─▶ sort numerically ─▶ ONE id-filtered verified page
                                            │
                                            ▼
                              completeness check ──miss──▶ abort, nothing signed
                                            │ok
                                            ▼
                            sign(JSON(hashes)) ─▶ POST once for the whole batch
```

Three properties of that diagram are load-bearing:

- **One page, not one GET per id.** The list path verifies every row and fetches the rules
  container once per call, so a 50-id approval costs one round trip and one container
  fetch. The per-id read it replaced cost both *per id*.
- **`includeForApproval` is required.** The rows being approved are pending, so the default
  list does not return them.
- **The completeness check is the guard.** A filtered page silently omits a row that failed
  verification, and an approval of fewer rows than the caller asked for is exactly what a
  single batch signature must never become. Every requested id must appear or the call
  aborts.

The contract service's raw-signature form (`approve(ids, signature, comment)`) is
**deprecated**: the signature is an opaque blob over hashes nothing verified, so the approver
cannot know what they signed.

### Approving a whitelisted address

Identical shape, and new — both the for-approval read
(`listWhitelistedAddressesForApproval`) and the approval (`approveWhitelistedAddresses`)
are generated in all four clients and were previously wrapped by **none** of them, so an
approver could not act on a whitelisted destination through the SDK at all, verified or
not. The for-approval read is verified and lenient (excludes and names unverifiable rows,
with `totalItems` reduced); the approval is strict and all-or-nothing.

`includeAlreadySignedByUser` is exposed on the read because it is what lets an approver
tell "waiting for me" from "waiting for someone else".

## Price Verification

`rate` and `decimals` feed amount conversion, so an unverified price is a wrong number a
caller acts on. Prices carry `signatures` made by a user holding the `PRICEUPDATER` role
(`Role` enum value 2, the same enum as `HSMSLOT`), and the signature covers the canonical
projection of the price — validatord's `CurrencyPrice`, exactly five fields in declaration
order:

```json
{"blockchain":"…","currencyFrom":"…","currencyTo":"…","decimals":"…","rate":"…"}
```

Reordering or extending that object silently changes every signature the SDKs accept.

**The verified container decides whether prices must be signed at all**, because it is the
only trustworthy statement on the subject: "this tenant has no price signer" comes from
SuperAdmin-verified data, whereas "this price carries no signatures" comes from the response
being checked.

```
  verified container ─▶ any PRICEUPDATER key? ──no──▶ PASS (tenant does not sign prices)
                                │yes
                                ▼
                        price.signatures empty? ──yes──▶ IntegrityError
                                │no                      (only the container may excuse
                                ▼                         a price from being signed)
                        one entry valid over the
                        canonical 5-field JSON? ──no──▶ IntegrityError
                                │yes
                                ▼
                               PASS
```

## Address Verification

Addresses carry a signature made by the HSM slot, proving the address was generated by the
hardware module rather than substituted in transit.

```
   rules container ──▶ user with the HSMSLOT role ──▶ HSM public key
                                                            │
   address.address ──── signed data (raw UTF-8 string) ──────┼──▶ ECDSA verify
   address.signature ── base64 r‖s ───────────────────────────┘
```

1. The address must carry a signature — absent is an error, not a silent skip.
2. The address string must be non-empty.
3. The HSM public key is found by locating the user holding the `HSMSLOT` role in the rules
   container. That container must itself have passed SuperAdmin verification first, or the
   HSM key would be attacker-supplied.
4. The signed data is the raw blockchain address string, UTF-8 encoded — not hex, not hashed.

Every failure raises `IntegrityError`; none returns a boolean. `RulesContainerCache` is
required at construction in every SDK, so this cannot be skipped.

## Request Metadata Verification

Requests carry `metadata.payloadAsString` (the string that is hashed) alongside a structured
`payload` object. **The SDKs deliberately do not expose the structured object**: an attacker
who altered it while leaving `payloadAsString` intact would leave the hash verifying, so every
field a caller reads is parsed from the hashed string.

```
   payloadAsString ──SHA-256──▶ computed ──constant-time compare──▶ metadata.hash
                                                     │
                                          ok ────────┴──── mismatch ──▶ IntegrityError
                                           │                            (includes both values)
                                           ▼
                             payload parsed, hashVerified = true
                                           │
                                accessors serve data ONLY from here
```

### Rules

- **Constant-time comparison.** Timing must not reveal how much of the hash matched.
- **Hash present but payload missing is an explicit error**, never a silent pass.
- **`hashVerified` is set wherever verification runs** — single-get and list alike. A caller
  checking the flag must not see `false` on a request that was in fact verified.
- **Accessors refuse unverified metadata.** `getSourceAddress`, `getDestinationAddress`,
  `getAmount` and friends raise a distinct unverified-metadata error rather than returning an
  empty value. "This field is not in the payload" and "I could not verify this payload" are
  different facts and must not share a representation.
- **List paths verify every row**, exclude the ones that fail, report the exclusions, and
  error if rows came back but none survived.
- **Every path verifies, through ONE seam.** `verifiedRequest(dto)` maps, verifies, marks
  and returns, and all nine paths go through it: `get`, the two list paths, and the six
  `create*` methods. The creates used to return the bare mapper output, so a request came
  back unverified and — once the approval path started demanding verification — could not
  be approved at all. No service method may call the request mapper directly.
- The error message includes the computed and provided hashes. They are derived from a payload
  the caller already holds, so they are not secret, and without them a mismatch is undebuggable.

### `hashVerified` means CONSISTENCY, not authenticity — and it is ADVISORY

It proves the payload string was not altered without also updating the hash. It does **not**
prove the pair came from Taurus-PROTECT: requests carry no client-verifiable signature, so an
interceptor rewriting *both* fields passes this check. Whitelisted addresses and assets are
different — those are signature-verified.

**The signing path does not read it.** The flag is serialized (Go
`json:"hash_verified,omitempty"`, a plain Pydantic field in Python, a compile-time-only
`readonly` in TypeScript), so a request rebuilt from JSON — a queue, a webhook, a cached
blob — can arrive claiming `true`. Java is the exception: its field is private with no
setter, though any reflective deserializer still sets it. So `approveRequests` re-runs the
verify primitive instead of trusting the flag: a SHA-256 over a string it already holds, no
network, and the same rule the whitelist approvals get by re-reading.

### Approval signing

0. Check each request carries a metadata hash, then **re-verify** that hash against its
   payload. `hashVerified` is not consulted (above). The presence check runs first so an
   early-status request still reports the clearer "no metadata hash".
1. Sort the requests by ID.
2. Build a JSON array of their `metadata.hash` values, compact (no spaces).
3. Sign those bytes with the caller's P-256 key; the signature is base64 raw r‖s.

## Cryptographic Primitives

| Operation | Algorithm | Notes |
|-----------|-----------|-------|
| Hash | SHA-256 | Payload integrity |
| Signature | ECDSA P-256 | SuperAdmin and user signatures |
| Comparison | Constant-time | Timing attack prevention |
| Encoding | Base64 | Signature transport |

## Error Types

### IntegrityError

Thrown when cryptographic verification fails:

- Hash mismatch (payload tampered)
- Insufficient valid SuperAdmin signatures
- Signature decode failure
- Cryptographic verification failure

### WhitelistError

Thrown for whitelist-specific failures:

- No matching rules for blockchain/network
- User signature verification failed
- Group threshold not met
- Hash not covered by any signature

---

## Security Properties

1. **Tamper Detection** - SHA-256 hash ensures data integrity
2. **Timing Attack Resistance** - Constant-time comparison
3. **Multi-Party Approval** - Governance requires threshold signatures
4. **SuperAdmin Authorization** - Rules must be signed by trusted admins
5. **Explicit Hash Coverage** - Signatures explicitly list covered hashes

---

## When Verification Happens

Always. There is no opt-out and no configuration that disables it:

- Every SDK **refuses to construct a client** without at least one SuperAdmin key.
- `minValidSignatures` must be positive and no greater than the number of keys supplied — a
  threshold nothing can satisfy is rejected at construction, not at the first call.
- Governance rules, whitelisted addresses, whitelisted assets and addresses all verify on
  every read path, single and list alike.
- `RulesContainerCache` is a constructor argument, not a setter, so address verification
  cannot be left unconfigured.

The verifier classes are also usable directly (`WhitelistedAddressVerifier`,
`WhitelistedAssetVerifier` and their peers) for offline or audit workflows over an envelope
you already hold.

## Selecting the governance rules

Step 5 asks *which* rules judge this entity, keyed on a `(blockchain, network)` pair through
three tiers:

```
   tier 1   exact blockchain + exact network      ── most specific
   tier 2   exact blockchain + wildcard network
   tier 3   wildcard blockchain                   ── global default, BROADEST
```

A wildcard is an empty value or `"any"`, matched case-insensitively in all four SDKs.

**The pair comes from the SIGNED payload, not from the surrounding DTO.** Nothing binds the
DTO to the signatures, so a response setting the blockchain to empty would select tier 3 —
broader than the rule the entity belongs to, and silently. Two failures, both closed:

- the payload omits the **chain** — an error, never treated as a wildcard;
- the payload and the DTO **disagree** on a field the payload carries — tampering or
  corruption, not a preference.

The **network** is treated differently: governance rules carry a per-rule
`includeNetworkInPayload` flag, and a correctly-signed payload omits `network` when it is off.
The DTO network is therefore used only when the payload genuinely carries none.

---

## Caching Verified Rules

For performance, verified governance rules are cached:

- **TTL** — configurable, default 5 minutes (Go: `protect.DefaultRulesCacheTTL`; the others:
  `DEFAULT_CACHE_TTL_MS`)
- **Invalidation** — manual cache clear available
- **Thread-safe** — safe for concurrent access; network I/O never happens while a lock is held
